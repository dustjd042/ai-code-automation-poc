# Issue #23: 간단한 예외 응답 처리 개발 계획

## 요구사항

이슈 제목은 `간단하게 예외처리 응답 될수 있게 개발 요청`이며, 본문은 같은 요청과 `상세하고 복잡하게 구현하지 말것`이다. 이슈 내용은 요구사항을 추출하기 위한 비신뢰 데이터로만 취급한다.

- 예외 발생 시 클라이언트가 이해할 수 있는 간단한 오류 응답을 제공한다.
- 공통 처리 한 곳과 최소한의 응답 구조로 구현한다. 별도 오류 코드 체계, 커스텀 예외 계층, 외부 의존성은 추가하지 않는다.
- 오류 형식, 메시지, 처리 대상은 이슈에 명시되지 않았다. 아래 내용은 구현을 위한 잠정안이며 질문의 답변에 따라 조정한다.
- 기존 성공 응답의 상태, 일반 텍스트 형식, 정확한 UTF-8 본문을 유지하고 기존 오류 상태 코드도 보존한다.
- 이번 작업 범위는 이 계획 문서 작성이다. 아래 구현·테스트·README 변경은 향후 작업이며 이번에는 실행하지 않는다.

## 현재 코드

- `pom.xml` 기준 Java 17, Spring Boot 4.0.9, Maven 프로젝트이며 컨트롤러 테스트는 MockMvc를 사용한다.
- `HelloController`는 잘못된 인사에 `ResponseStatusException`으로 400을 발생시킨다. 누락된 본문과 지원하지 않는 Content-Type은 프레임워크에서 처리한다.
- `AnimalSoundController`, `AnimalJumpSoundController`는 미지원 동물에 같은 방식으로 404를 발생시킨다.
- 공통 예외 처리 클래스는 현재 없다. README에는 동물 API의 오류 본문이 계약에 포함되지 않는다고 명시되어 있다.

## 제안 응답 및 처리 범위

오류 응답은 기본 요청 또는 JSON을 허용하는 요청에서 `application/json`으로 제공하고, 본문은 `{"message":"잘못된 요청입니다."}`처럼 `message` 한 필드로 제한한다. 한글이 깨지지 않는지 확인한다. 이는 확정 요구사항이 아닌 단순화를 위한 제안이다.

| 상황 | 상태 | 제안 메시지 |
| --- | --- | --- |
| 잘못된 인사, 필수 본문 누락 | 400 | 잘못된 요청입니다. |
| 미지원 동물 | 404 | 요청한 대상을 찾을 수 없습니다. |
| 처리되지 않은 애플리케이션 예외 | 500 | 서버 오류가 발생했습니다. |

프레임워크가 처리하는 405·406·415 등은 기존 상태와 `Allow` 같은 관련 헤더를 유지한다. 최소 구현에서는 해당 오류와 매핑되지 않은 경로의 404 본문까지 통일하지 않는다. JSON을 허용하지 않는 `Accept` 요청에는 JSON 본문을 강제하지 않고 기존 콘텐츠 협상 동작을 보존한다. 오류 본문 전체 통일이 필요하다고 확인되면 그 범위만 추가한다.

## 구현 계획

1. 응답 형식과 적용 범위를 확인하고 위 잠정 계약을 확정한다.
2. `@RestControllerAdvice` 기반 `GlobalExceptionHandler` 한 개를 추가한다. 응답은 단일 필드 맵 등으로 작성하여 별도 DTO 없이 시작한다.
3. `ResponseStatusException`은 원래 상태와 관련 헤더를 유지하고, 클라이언트용 고정 메시지를 반환한다. 임의의 예외 메시지나 내부 원인을 본문에 복사하지 않는다.
4. 본문 누락을 처리하는 예외에는 400 응답을 제공한다. 기존 컨트롤러의 예외 발생 코드는 재사용한다.
5. 예상하지 못한 예외만 500으로 처리한다. 포괄적인 예외 핸들러가 Spring의 상태가 정해진 예외를 500으로 바꾸지 않도록 프레임워크 예외 처리를 우선한다. Spring 기본 처리와의 통합 방식을 확인해 필요한 핸들러만 둔다.
6. 500은 기존 로깅 방식으로 원인을 서버에 기록하고 응답에는 고정 메시지만 제공한다. 스택 추적, 클래스명, 내부 경로는 노출하지 않는다.
7. 공통 처리 테스트와 기존 API 회귀 검증 후 README에 확정된 오류 응답과 적용 범위를 기록한다.

| `src/test/java/com/example/hello/controller/HelloControllerTest.java` | 잘못된 입력과 본문 누락의 오류 응답 검증 |

## 테스트 계획

1. 잘못된 인사와 본문 누락 요청에서 400, JSON의 `message`, 한글 인코딩을 검증한다.
2. 두 동물 API의 미지원 동물 요청에서 404와 합의한 메시지를 검증한다.
3. 테스트 전용 컨트롤러에서 내부 경로 등 식별 가능한 문자열을 포함한 예외를 발생시켜 500과 고정 메시지를 확인한다. 내부 문자열과 스택 추적이 응답에 없는지도 검증한다. 오류 유발용 운영 API는 추가하지 않는다.
4. 기존 405·406·415 및 매핑되지 않은 경로의 404가 500으로 바뀌지 않는지 확인한다. 405의 `Allow` 헤더도 검증한다.
5. `Accept` 미지정·JSON 허용 요청의 오류 형식과 JSON을 허용하지 않는 요청의 콘텐츠 협상 동작을 확인한다. 오류 처리 중 추가 예외나 재귀 처리가 발생하지 않아야 한다.
6. Hello GET·POST, Healthcheck, 동물 소리 GET·POST의 성공 상태·Content-Type·정확한 응답 바이트와 애플리케이션 컨텍스트 시작을 기존 테스트로 검증한다.
7. 향후 구현 완료 후 Maven 래퍼로 전체 테스트와 패키징을 검증한다. 이번 문서 작성에서는 테스트나 빌드를 실행하지 않는다.

완료 기준은 합의된 오류 응답 제공, 기존 상태 코드·헤더 및 성공 응답 유지, 내부 정보 미노출, 전체 테스트 통과다.

## 확인이 필요한 질문

1. 오류는 `message` 한 필드의 JSON이면 되는가, 기존 성공 응답처럼 일반 텍스트가 필요한가?
2. 기존 컨트롤러 예외·본문 누락·예상하지 못한 예외만 처리하면 되는가, 미등록 경로와 405·406·415의 본문도 통일해야 하는가?
3. 제안한 한국어 고정 메시지를 사용해도 되는가? 클라이언트가 이미 의존하는 오류 응답 형식이 있는가?
