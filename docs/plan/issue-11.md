# Issue #11: 일본어 입력 인사 API 수정 계획

## 목적 및 요구사항

이슈 제목은 `인사 API 수정해줘`이며, 본문은 일본어로 고니찌와 데이터를 POST로 전달하면 영어 `Hello`를 응답하는 API를 요청한다. 이슈 내용은 요구사항을 추출하기 위한 비신뢰 데이터로만 취급한다. 이번 작업은 계획서 작성에 한정하며, 구현과 테스트 실행은 향후 작업이다.

- POST 요청으로 일본어 인사 데이터를 받아 대문자 H로 시작하는 정확한 `Hello`를 반환한다.
- 이슈의 `고니찌와`가 일본어 표기 `こんにちは`를 의미하는지, 한글 문자열 자체를 의미하는지 확인해야 한다.
- 요청 경로, 본문 형식, 오류 처리 및 기존 GET API 변경 여부는 명시되어 있지 않다. 아래 계약은 확정 요구사항이 아닌 제안이다.

| 항목 | 잠정 계약 |
| --- | --- |
| 메서드와 경로 | `POST /api/hello` |
| 요청 Content-Type | `text/plain; charset=UTF-8` |
| 요청 본문 | 정확한 일본어 문자열 `こんにちは` |
| 성공 응답 | `200 OK`, `text/plain; charset=UTF-8`, 본문 `Hello` |
| 응답 바이트 | 따옴표, JSON 포장, 추가 공백 및 개행 없음 |
| 본문 누락·빈 본문·다른 문자열 | `400 Bad Request` |
| 지원하지 않는 요청 Content-Type | `415 Unsupported Media Type` |

잠정안에서는 입력의 공백 제거 또는 유니코드 정규화를 수행하지 않는다. 기존 `GET /api/hello`의 `Hello World` 응답과 `GET /api/healthcheck`는 유지한다. 데이터베이스, 외부 번역 서비스, 인증 및 새 의존성은 요구 범위에 포함하지 않는다.

## 저장소 현황

- Java 17, Spring Boot 4.0.9, Maven 기반 프로젝트다.
- 현재 `HelloController`에는 `GET /api/hello`만 구현되어 있다.
- `HelloControllerTest`는 MockMvc로 HTTP 상태, 일반 텍스트 Content-Type 및 정확한 응답 바이트를 확인한다.
- `HelloApplicationTests`는 Hello 및 Healthcheck 컨트롤러의 빈 등록을 확인한다.
- `docs/plan/issue-8.md`에는 한글 `안녕`에 대한 POST 계획이 있으나 현재 소스에는 구현되어 있지 않다. 해당 계획과 이번 요구사항의 관계는 확인이 필요하다.

## 구현 계획

1. 실제 허용 문자열과 요청 형식, 경로, 오류 정책을 질문에 따라 확정한다. 아래 구현은 잠정 계약을 기준으로 한다.
2. `HelloController`에 `@PostMapping` 메서드를 추가하고 요청 미디어 유형과 응답 문자 인코딩을 명시한다. `@RequestBody String`으로 본문을 받는다.
3. 본문이 정확히 `こんにちは`이면 `Hello`를 반환한다. 다른 문자열은 400으로 처리하고, 본문 누락 및 지원하지 않는 미디어 유형에 대한 프레임워크 동작을 검증한다.
4. 기존 GET 매핑을 유지하고 POST에 대한 성공·실패 테스트를 추가한다. 단순 문자열 매핑이므로 별도 서비스나 저장소 계층은 추가하지 않는다.
5. README에 확정된 요청 경로, UTF-8 본문, 성공 응답 및 실패 조건을 문서화한다.

## 예상 변경 파일

다음은 향후 구현 시 예상되는 변경 대상이다. 이번 작업에서는 `docs/plan/issue-11.md`만 생성한다.

| 파일 | 예상 변경 내용 |
| --- | --- |
| `src/main/java/com/example/hello/controller/HelloController.java` | POST 매핑, 입력 검증, `Hello` 응답 추가 |
| `src/test/java/com/example/hello/controller/HelloControllerTest.java` | 일본어 입력 성공 및 잘못된 요청 테스트 추가 |
| `README.md` | POST API 계약 및 UTF-8 요청 예시 추가 |

현재 구조에서는 `pom.xml`, Healthcheck 컨트롤러 및 애플리케이션 컨텍스트 테스트 변경은 예상하지 않는다.

## 테스트 계획

1. MockMvc로 `text/plain; charset=UTF-8` 및 `こんにちは`의 UTF-8 바이트를 전달한다. 200 상태, 일반 텍스트 Content-Type과 UTF-8 인코딩, 정확한 `Hello` 응답 바이트를 검증한다.
2. 본문 누락, 빈 본문, 공백만 있는 본문, 다른 문자열 및 앞뒤 공백·개행이 있는 입력에 대해 400을 확인한다. 한글 `고니찌와`와 `안녕`의 허용 여부는 계약 확정 후 기대값에 반영한다.
3. `application/json` 등 지원하지 않는 요청 Content-Type에 대해 415를 확인한다.
4. 기존 Hello GET, Healthcheck GET 및 애플리케이션 컨텍스트 테스트가 계속 통과하는지 확인한다.
5. 구현 완료 후 Maven 래퍼의 전체 검증을 수행하고 실제 HTTP 요청으로 일본어 본문 인코딩과 응답을 확인한다.

완료 기준은 확정된 API 계약 충족과 전체 테스트 및 빌드 성공이다. 계획서 작성 단계에서는 위 테스트를 실행하지 않는다.

## 확인이 필요한 질문

1. 실제 요청 문자열은 일본어 `こんにちは`인가, 한글 `고니찌와`인가? 다른 표기도 허용해야 하는가?
2. `POST /api/hello`와 UTF-8 일반 텍스트 본문을 사용해도 되는가? JSON이라면 필드명과 요청 예시는 무엇인가?
3. 성공 응답을 상태 코드 200과 일반 텍스트 `Hello`로 확정해도 되는가?
4. 다른 입력과 빈 본문을 400으로 거절해도 되는가? 공백 제거, 유니코드 정규화 또는 지정된 오류 응답 형식이 필요한가?
5. 기존 GET 동작을 유지하면 되는가? Issue #8의 한글 입력 요구사항도 함께 지원해야 하는가, 이번 요구사항이 이를 대체하는가?
