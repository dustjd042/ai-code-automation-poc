# Issue #19: 거북이·토끼 뛰는 소리 POST API 개발 계획

## 요구사항 및 범위

이슈 제목은 `거북이 토끼 뛰는 소리 api`이며, 본문은 `거북이 토끼 뛰는 소리 api post 만들어줘`이다. 이슈는 요구사항 추출을 위한 비신뢰 데이터로만 취급한다. 이번 작업은 계획 문서 작성에 한정하며, API 구현과 테스트 실행은 향후 작업이다.

- 명시된 요구사항은 거북이와 토끼의 뛰는 소리를 제공하는 POST API다.
- 소리가 의성어 문자열인지 실제 오디오인지, 동물 선택 방식, 경로, 요청·응답 형식 및 정확한 소리는 명시되어 있지 않다.
- 아래 계약은 의성어 문자열을 반환한다고 가정한 제안이다. 소리 값은 임의로 확정하지 않으며 구현 전에 확인한다. 실제 오디오가 필요하다면 파일 형식, 음원 확보와 이용 권한, 저장·전송 방식을 다시 설계한다.
- 기존 Hello GET·POST 및 Healthcheck API 동작을 유지한다. 문자열 잠정안에는 데이터베이스, 외부 서비스, 새 의존성 또는 인증 기능 추가를 포함하지 않는다.

## 저장소 현황

- Java 17, Spring Boot 4.0.9, Maven 기반 프로젝트다.
- `HelloController`는 `GET /api/hello`와 일본어 인사를 받는 `POST /api/hello`를 제공한다.
- `HealthcheckController`는 `GET /api/healthcheck`를 제공한다.
- 기존 컨트롤러 테스트는 MockMvc로 상태, 미디어 유형 및 정확한 응답 바이트를 검증하고, `HelloApplicationTests`는 컨트롤러 빈 등록을 확인한다.
- Issue #14 계획에는 강아지·고양이 소리 GET API가 제안되어 있지만 현재 소스에는 구현되어 있지 않다. 해당 계획을 구현된 기능으로 전제하지 않는다.

## 제안 API 계약

다음은 구현을 구체화하기 위한 잠정안이며, 확정된 요구사항은 POST 메서드와 거북이·토끼의 뛰는 소리 제공이다.

| 항목 | 잠정 계약 |
| --- | --- |
| 메서드 및 경로 | `POST /api/animals/{animal}/jump-sound` |
| 동물 식별자 | 소문자 `turtle`, `rabbit` |
| 요청 본문 | 필요 없음; 동물은 경로로 선택 |
| 성공 상태 | `200 OK` |
| 성공 Content-Type | `text/plain;charset=UTF-8` |
| 성공 본문 | 동물별로 합의한 뛰는 소리 문자열; 정확한 값은 미정 |
| 응답 바이트 | UTF-8, 따옴표·JSON 포장·추가 공백·개행 없음 |
| 지원하지 않는 동물 | `404 Not Found` |
| 동물 식별자가 없는 경로 | 매핑 없이 `404 Not Found` |
| 지원하지 않는 메서드 | 동일 경로의 GET 등은 `405 Method Not Allowed` |
| 허용되지 않는 응답 미디어 유형 | `Accept: application/json` 등은 `406 Not Acceptable` |

잠정안은 자원 생성이나 상태 변경 없이 소리를 즉시 반환한다. 대소문자 변환, 공백 제거 및 한글 별칭은 제공하지 않는다. 요청 본문을 바인딩하지 않으므로 본문이 전달되어도 사용하지 않으며, 요청 Content-Type을 제한하는 `consumes` 조건은 두지 않는다. 오류 본문은 별도 합의가 없으면 정확한 문자열로 고정하지 않는다.

## 구현 계획

1. 문자열·오디오 여부, 두 동물의 정확한 소리 값, 경로와 입력·오류 정책을 질문을 통해 확정한다. 이후 단계는 위 문자열 잠정안 기준이다.
2. 기존 컨트롤러 패키지에 `AnimalJumpSoundController`를 추가한다. `@PostMapping`과 경로 변수로 동물을 선택하고 응답 미디어 유형과 UTF-8을 명시한다.
3. `turtle`과 `rabbit`을 확정된 문자열에 매핑하고 그 외 식별자는 404로 처리한다. 두 고정 값을 반환하는 범위에서는 별도 서비스·저장소 계층을 추가하지 않는다.
4. 새 컨트롤러의 MockMvc 테스트와 애플리케이션 컨텍스트의 빈 등록 검증을 추가한다.
5. README에 확정된 POST 경로, 동물 식별자, 본문 필요 여부, 정확한 응답 값과 오류 정책을 기록한다.
6. 전체 테스트 및 빌드로 신규 계약과 기존 API 회귀 여부를 검증한다.

## 테스트 계획

1. `turtle`, `rabbit` 각각에 본문 없는 POST 요청을 보내 200, `text/plain;charset=UTF-8`, 합의한 소리의 정확한 UTF-8 응답 바이트를 검증한다. 따옴표·공백·개행 추가 여부도 확인한다.
2. `bird`, `Turtle`, `RABBIT` 및 한글 별칭에 대해 404를 검증한다. 한글 경로는 적절히 URL 인코딩한다.
3. 동물 식별자가 없는 `/api/animals/jump-sound` 요청의 404와 정상 경로에 대한 GET 요청의 405를 확인한다.
4. 정상 POST 경로에 `Accept: application/json`을 지정하면 406인지 검증한다. 오류 본문은 고정하지 않는다.
5. 본문과 요청 Content-Type을 지정하지 않아도 성공하는지 확인한다. 본문을 무시하는 잠정 정책이 확정되면 본문을 보낸 요청도 같은 결과인지 검증한다.
6. 기존 Hello GET·POST의 성공·실패 테스트, Healthcheck 테스트 및 새 빈 등록을 포함한 컨텍스트 테스트가 통과하는지 확인한다.
7. 구현 완료 후 `./mvnw clean verify`로 전체 검증을 수행하고 실제 HTTP 응답의 한글 인코딩을 확인한다. 이는 향후 테스트 계획이며 이번 문서 작성에서는 실행하지 않는다.

완료 기준은 정확한 두 소리 값 등 미정 계약의 확정, 해당 계약에 따른 POST 응답과 오류 처리, 기존 API 회귀 없음 및 전체 테스트·빌드 성공이다.

## 확인이 필요한 질문

1. 뛰는 소리는 의성어 문자열인가, 재생 가능한 실제 오디오인가? 거북이와 토끼 각각의 정확한 소리 또는 음원은 무엇인가?
2. `POST /api/animals/{animal}/jump-sound`와 `turtle`·`rabbit` 식별자를 사용해도 되는가? 동물을 JSON 본문으로 전달하거나 두 동물의 소리를 한 번에 반환해야 하는가?
3. UTF-8 일반 텍스트로 응답하면 되는가, 동물명과 소리를 포함한 JSON이 필요한가?
4. POST는 소리 반환만 수행하면 되는가, 재생 이벤트 생성·저장 등 상태 변경도 필요한가?
5. 미지원 동물은 404로 처리해도 되는가? 한글 별칭, 대소문자 무시, 본문 무시 대신 거절, 지정된 오류 형식이 필요한가?
6. Issue #14의 강아지·고양이 소리 계획과 공통 API 형태로 맞춰야 하는가, 별개 기능으로 진행하면 되는가?
